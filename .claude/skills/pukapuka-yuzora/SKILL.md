# pukapuka 夕空スキル

夕空（`src/components/WordCloudOverlay.tsx`。水辺の画面に重ねて出す）を、**本物のスマホで測って、課題を見つけて、直して、測り直す**。
何を作るか・なぜかは `docs/SPEC.md`、色・見た目の決まりは `/pukapuka-design`（「夕空」の節）、アプリ全体の重さ・熱は `/pukapuka-perf`、星空のつまむ・なぞるは `/pukapuka-night`。

**決まり**
- **いつも「診断 → 課題を1つ選ぶ → 直す → 測り直す → このスキルを直す」を1周にして、くり返す**（ユーザー「課題を見つけ、常に画面のボタンが押せないとか、ズームとかなぞりとか、遅い感じがあるから、常に自己改善してほしい」2026-10-14）
- 夕空のコードを変えたら、報告の前に必ず `check.sh` を1回通す。数字は 4. の表に1行書く
- **直す前に測る。1回に1つだけ直す。** 悪くなったらすぐ戻す
- 見た目が変わる直し（光を減らす・言葉を減らすなど）は、案と見本を見せて、ユーザーの「はい」のあとで
- 「直った」と言う前に、スマホで確かめる。adb でできないこと（2本指でつまむ）は、確かめていないとはっきり書いて、ユーザーに触ってもらう
- 報告は日本語。数字は表と短い文で

## 2. 健康診断（`check.sh`、約2分半）

**始める前に**：スマホで Expo Go が前面にあり、夕空が開いていること（見本は閉じている）。開いていなければ、水辺の右上の月 → 「夕空」。スマホのつなぎ方は `/pukapuka-perf` の 2.

| 項目 | 何を見るか | 目安（止めどき） |
|---|---|---|
| ボタン（見本を見る・×・星空へ・水辺へ） | ○ 押せた／✗ 押せない、押してから変わるまで、画面がいちばん長く止まった時間 | 全部 ○。止まった時間 100ms 以下（1コマ17ms。100ms を超えると「もたつく」と感じやすい） |
| なぞり始め（1倍・2倍） | 指をおいてから言葉が動き始めるまで | 100ms 以下 |
| なぞる（見本・2倍・ふだん） | 遅れたコマの割合（カクつき）、遅いほうから10%のコマの時間 | 遅れ 5% より下、90%のコマ 16ms 以下 |
| じっと（見本・2倍・ふだん） | CPU（100%＝芯1つぶん。熱の原因） | まだ決めていない。ユーザーと決める |
| 注意・エラー | 黄色・赤の知らせ（`ReactNativeJS` の W/E）の数と中身 | 0 |

**速く比べるとき**：`QUICK=1` を付けると、見本の出し入れだけを3回測る（約1分）。直す前と後を比べるとき。言葉が入れかわる直しは、こちらで足りる

**原因をしぼる手**：疑わしい部品を一時的に消して（`cp` で元を取ってから `return null`）、`QUICK=1` で測る。消して良くなれば、それが原因。終わったら `cp` で戻して `git diff` で確かめる

**画像（`assets/`）を足すと、アプリ全体が読み込み直されて水辺に戻る**。測る前に `river_cloud`（`lib.sh`）で夕空へ

**web の確かめ**：`node docs/talk/day/render-yz-web.mjs 出力.png`（8091 で web を立ててから。夕空の見本を撮る）

**測り方の仕組み**（変えるときに知っておくこと）
- 押す・なぞるの反応は、スマホの「タップを表示」（`show_touches`）をつけて録画（`screenrecord`、半分の大きさ）し、指の印が出たコマと、決めた所が変わったコマの差で出す。録画は画面が変わったときだけコマができるので、コマの間があいた＝画面が止まっていた
- 指の印は、録画に出ないことがある（「星空へ」で一度も出なかった）。そのときは「変わるまで」は出さず、押せたかと止まった時間だけ出す
- 終わったら `show_touches` を 0 に戻す（`trap`）。途中で止めたときは、`adb shell settings put system show_touches 0`
- 2本指でつまむは、adb の `input` では送れない。ユーザーに触ってもらう

## 3. 1周の進め方

1. **診断**：`check.sh` を通す。1回目は温まる前なので、気になる数字はもう1回測る
2. **課題を選ぶ**：目安を外れたもの → ユーザーに言われたもの → 5. の候補、の順。1つだけ
3. **原因をしぼる**：コードを読んで、仮説を立て、測って確かめる（当てずっぽうに部品を止めない）
4. **直す**：1つだけ。`npx tsc --noEmit -p .`
5. **測り直す**：同じ `check.sh`。悪くなったら戻す。見た目は撮って確かめる
6. **記録**：4. の表に1行。コミット（PR のブランチ）
7. **自己改善**：まちがえたこと・時間がかかったことを 6.・7. に書き、`check.sh` や手順を直してから次の周へ
8. 3周して良くならなければ、分かったことと次の候補をユーザーに報告して、方針を聞く

## 5. 課題の候補（見つけたら足す。直したら 8. へ移す）

- **動画の読み込み待ち（約1.2秒）の間、静止画のまま止まって見える**（夕空へ・水辺へ）。開発中（Expo Go）は、動画をトンネル越しに PC から読むので遅い。web 版・本番は未測定。手：①先に読み込んでおく（2本目のプレーヤー。前に Android で困ったので慎重に）②待つ間も泡が昇り始める（見た目が変わるのでユーザーに聞く）
- **触りはじめと離したときに、画面全体を作り直している**：`useAnimatedReaction` → `runOnJS(setZoomed)` で React の再描画が走る（`renderToHardwareTextureAndroid` を切り替えるため）。adb のなぞりでは止まり19〜65ms で目立たないが、本物の指・つまむでは未確認。手：上と同じ `memo`、または拡大中だけ切り替える
- **じっとしているときの CPU が 70〜85%**（見本は85%）。光のまたたき（`clock`）と背景の動画。拡大して止めると約60%。熱が気になったら、またたきの層の数（`SPARKLE_GROUPS`）や光の描き方を見る（見た目が変わるので、ユーザーに聞いてから）
- **つまむ（2本指）**：adb で確かめられない。ユーザーに「重い・遅い」と言われたら、どんなときか（拡大の途中か・離したときか）を聞く
