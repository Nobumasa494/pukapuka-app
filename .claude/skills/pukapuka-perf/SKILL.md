# pukapuka 重さ・熱・バグのスキル

アプリ全体（水辺・夕空・星空と、その移り変わり）の **重さ・熱・バグ** を、本物のスマホで測って直す。
星空の中だけの直し方（なぞる・つまむ・星のまたたき）は `/pukapuka-night` の 5.・6. にくわしい。見た目を変えるときは `/pukapuka-design`。

**決まり**
- **直す前に測る。** 原因が分かる前に作りを変えない（2026-10-09、押す仕組みを先に入れ替えて悪くした）
- **1回に1つだけ直す。** まとめて直すと、どれが効いたか分からない
- **同じ手順・同じ条件で測り直す。** 測った数字は、下の「4. 記録の表」に必ず書く
- 目標（止めどき）は、ユーザーと決めてから始める
- **いつも「最適化 → 時間短縮 → 自己改善」までを1つの周にして、くり返す**（ユーザー「常に時間短縮、自己改善、最適化までを繰り返してね」2026-10-10）。直して終わりにしない。毎周、何に時間がかかったかを 7. に書き、次の周の手順・道具を直してから始める
- 返事・報告は日本語で、数字は表と短い文で。用語（CPU・コマなど）は、初めて出たところで一言説明する

## 1. 測るもの

| 名前 | 何を見るか | 取り方 | 目安 |
|---|---|---|---|
| 遅れたコマ（遅れ） | 1秒60コマのうち、間に合わずカクついたコマの割合 | `dumpsys gfxinfo host.exp.exponent` の Janky frames | 5%より下ならなめらか |
| CPU | スマホの頭脳をどれだけ使っているか。100%＝芯1つぶん。熱の一番の原因 | `top -b -n 1` の Expo Go の行 | 星空は約97%（2026-10-09）。水辺は約190%（重い） |
| 温度 | 電池の温度 | `dumpsys battery` の temperature ÷10 | 40℃を超えると「熱い」と感じやすい |
| メモリ | 使っている記憶の量。増え続けると、いつか落ちる | `dumpsys meminfo` の TOTAL PSS | 移り変わりをくり返しても増え続けないこと |
| 移り変わり | 止まる・黒くなる・落ちる・エラー | `transitions.sh` で何周も行き来し、各画面を撮る | 全周で ⚠ が0、エラー0 |

## 2. 道具（`scripts/perf/`。`PHONE=IP:ポート` を付けて使う）

- `lib.sh`：共通（読み込み直し・画面の移り変わり・測る）。座標は Galaxy S20（1080×2400）
- `measure.sh [秒]`：水辺・夕空・星空・水辺（戻り）に、それぞれ N 秒（ふつう10秒）いて測る
- `transitions.sh [周]`：水辺 → 夕空 → 星空 → 夕空 → 水辺 → 星空 → 水辺 を N 周。画面が真っ黒・真っ白なら ⚠。最後にエラーの記録と、水辺の重さ
- 星空の中の細かい測り方（なぞる間・星を押した反応）は `scripts/night/phone/perf.sh`

**つなぎ方**（1回だけ。ユーザーにしてもらう）：スマホの 設定 → 開発者向けオプション → ワイヤレスデバッグ →「ペア設定コードによるデバイスのペア設定」の6桁と IP:ポートを教えてもらう → `adb pair` → `adb mdns services` で接続用のポートを見つけて `adb connect`。ポートは毎回変わる。adb は `~/.local/android/platform-tools/adb`

**操作する前に**：Expo Go が前面か確かめる（`lib.sh` の `need_expo`）。前面でなければ止めて、ユーザーに開いてもらう。ユーザーがスマホを使っている間は操作しない

## 3. 1周の進め方

1. **測る**：`measure.sh` を2回（1回目は温まる前なので、2回目の数字を使う）。移り変わりを変えたときは `transitions.sh 5` も
2. **原因をしぼる**：一番重い画面を選び、その画面で動いているものを1つずつ止めて測る（例：泡の揺れ・水面の動画・またたき・曲）。止め方は、試しの前に `cp` で元を取っておき、試しのあとは戻して `git diff` で確かめる
3. **1つだけ直す**
4. **測り直す**：1 と同じ手順・同じ秒数で
5. **悪くなったら、すぐ戻す**。良くなったら、見た目が変わっていないかを撮って確かめる
6. **記録する**：下の表に1行。コミット
7. **時間を振り返る**：この周で時間がかかったこと・むだだったことを 7. の表に1行。道具（`scripts/perf/`）やこのスキルの手順を直して、次の周を速くする
8. **自己改善**：測り方や判断のまちがい（例：開発用の読み込み直しのメモリをアプリのせいと思う）を見つけたら、5.・6. と「決まり」に書き足す
9. 止めどきに届くまで、1〜8 をくり返す。**3周しても良くならなければ**、分かったことと次の候補をユーザーに報告して、方針を聞く

**時間を短くする**（星空で分かったこと）
- 読み込み直しは R を2回（約12秒）。アプリを閉じて開かない
- サーバーを起動し直したあとは、スマホが古いコードのままのことがある。まず画面を撮って、新しいコードか確かめる
- `uiautomator dump` はアニメーション中に失敗する。`screencap` を ffmpeg で切り出して見る
- 光る・動くものは静止画では分からない。`adb shell screenrecord --time-limit 6` で録って、コマに切って見る

## 5. 分かっている候補

**2026-10-10 に確かめたこと**
- **どの作業が重いか**は、まず作業（スレッド）ごとに見る：`adb shell top -H -b -n 2 -d 3 -p <pid> -o TID,%CPU,CMD`（2回目の表を使う）。水辺では 画面の作業（UI スレッド `st.exp.exponent`）65%・描く作業（`RenderThread`）50%・JS 8%・動画と音 数%ずつ。**JS ではなく、毎コマ描き直すことが重い**
- 泡の毎コマの計算（`useFrameCallback`）を止めると、水辺の CPU 約140% → 約70%（泡が動かなくなり、描き直しもなくなるため）
- 止めても変わらなかったもの：泡ごとの文字・もやの毎コマの計算、泡の影（`boxShadow`）、泡の位置の計算を1コマ1回にする（約153% → 約148%。ぶれの範囲。カクつきは 5.4% → 4.3%）
- 背景の動画が毎コマ流れているので、泡の数を減らしたり泡だけ30コマにしたりしても、画面は毎コマ描き直される
- メモリ：開き直した直後 約780MB、画面を60回行き来して約1000MB（1周20MBずつ、ゆっくり増える）。**3.4GB で落ちたのは、開発用の読み込み直し（R）を何十回もしたため**。読み込み直しのたびに、動画・音のプレーヤーが前の分も残る（開いた直後14個 → 何度も読み込み直したあと27個）
- 音のプレーヤーは、開いた直後から14個（曲3・チャイム5種×2・動画1）。行き来しても増えない
- 本番に近い形（別のサーバー `npx expo start --port 8092 --tunnel --no-dev --minify` を立てて、`am start -d exp://<hostUri>` で開く）でも、水辺は約153%で変わらない。重さは JS ではなく、画面を描く側。測り終えたら 8092 は止め、スマホを 8081 に戻す（ユーザーの 8081 は止めない）

**まだ確かめていない候補**

- 水辺：泡ごとの揺れの計算（`useFrameCallback`）、背景の動画、泡の数
- 画面が見えていない間も動き続けるもの（星空のスキル 5. の「見えない川の泡が毎コマ揺れていた」と同じ形）。夕空のキラキラ、月と星・星の見方の「きらん」（4秒に1回）、星空のまたたき
- 移り変わり：動画の差し替え（`playClip`）と静止画の重ね方

| 日付 | 起きたこと | 原因 | こうする |
|---|---|---|---|
| 2026-10-10 | 測定の途中でアプリが落ち、数字が空になった | メモリ約3.4GB で「NO MEMORY」。開発中の読み込み直し（R）を何十回もしたあと | 測る前に Expo Go を開き直して、メモリを空にしてから測る。メモリは毎回記録する。落ちたかは `adb logcat -d -b crash` の Abort message で見る |
