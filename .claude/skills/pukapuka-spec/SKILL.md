# pukapuka 設計書スキル

設計書 `docs/SPEC.md` を書く・直すためのスキル。**書く → 自分で見直して問題を洗い出す → 直す** を、問題が出なくなるまで繰り返す。
見た目は `/pukapuka-design`、音は `/pukapuka-music`、背景の絵は `/pukapuka-blender`。このスキルは「何を作るか・なぜか」を書く設計書の担当。

---

## 1. 設計書の決まり（守ること）

### 読みやすさ（ユーザー指摘 2026-10-05「設計書が難しい」）
- **やさしい日本語で、短い文で書く**。1文に1つのことだけ
- 専門用語（PageRank・強連結成分分解・共起など）は、初めて出る所で**1行の説明**を付ける。説明できない言葉は使わない
- 各セクションの最初に**2〜3行のまとめ**を置く。細かい数値・経緯は後ろに
- 表は「何のため」から書く（計算の名前から書かない）

### pukapuka の決まり（設計書のどこにも、これに反することを書かない）
- 目的は**ユーザーが自分で気づく**こと。アプリが「あなたはこういう人」と断定しない
- **分析されている感覚を持たせない**。数字・順位・グラフを見せず、変化は景色で表す
- ゴールは**ワクワクを育てる**（ワクワクの島が育っていく）。分析はそのための手段
- ノルマ・連続記録・点数・助言（「〇〇しないで」）を作らない
- ユーザーが決めたことは**日付と理由（できればユーザーの言葉）**つきで書く

### 「決まったこと」と「案」を分ける
- ユーザーが決めたこと＝**決定**。私が考えたこと＝**案**と書く。案を決定のように書かない
- 決まっていないことは「未決事項」の表へ

---

## 2. 手順（この順番で）

1. **SPEC.md 全体を読む**（変える所だけ読まない。ほかの所と食い違うことがある）
2. **今回の変更を書く**（決定と案を分けて）
3. **見直す**: 下の「3. 見直しのチェックリスト」を上から全部当てて、問題点を箇条書きで出す。自分の書いた所だけでなく、**関係するほかのセクションも**見る
4. **直す**: 出た問題を直す。直せないもの（ユーザーが決めること）は「ユーザーに聞くこと」に回す
5. **3 と 4 をくり返す**。止めどきは「4. 止めどき」
6. **報告する**（「5. 報告の形」）

---

## 3. 見直しのチェックリスト

### 食い違い
- [ ] 同じことが2か所に書かれていて、内容がずれていないか（数値・状態・名前）
- [ ] 「画面構成」の状態（✅／🔧）、「将来追加する機能」「未決事項」が、本文と合っているか
- [ ] コードと合っているか（ファイル名・関数名・数値。必要ならコードを読んで確かめる）

### pukapuka の決まりに反していないか
- [ ] 断定していないか（「あなたは〜」「〜が原因」）
- [ ] 分析されている感覚を与えないか（数字・順位・グラフ・「分析」という言葉を画面に出していないか）
- [ ] ノルマ・点数・助言になっていないか

### データのかたより（分析を書いたとき）
- [ ] **川が決めてしまうこと**を、ユーザーの気持ちとして扱っていないか（同じ回の中の拾う順番・流れてきた言葉の数）
- [ ] 時間帯のかたより（夜に開く人は夜の言葉が多い）を考えているか
- [ ] 偶然でも起きることと比べているか
- [ ] データがどれくらいたまれば意味が出るか書いてあるか（少ない間の見せ方も）
- [ ] 「順番」を「原因と結果」と書いていないか

### 読みやすさ
- [ ] 説明なしの専門用語がないか
- [ ] 1文が長すぎないか（目安 60 字）
- [ ] セクションの最初にまとめがあるか

### 実現できるか
- [ ] 今の作り（React Native＋Convex、言葉は決まった約100語）でできるか。できないなら、何が足りないか書いてあるか
- [ ] スマホで重くならないか（星や泡の数、毎コマの計算）

---

## 4. 止めどき

- チェックリストを全部当てて**新しい問題が出なくなったら**止める
- **最大3周**。3周しても出る問題は、ユーザーが決めること（方針・好み）のことが多いので、自分で決めずに「ユーザーに聞くこと」として報告する
- 私には「満足」の感覚がないので、**チェックリストを通ったこと**を止める理由にする。「よくなった気がする」では止めない

---

## 5. 報告の形

```
【今回書いたこと】（決定と案を分けて、2〜5行）
【見直しで見つけて直したこと】（周ごとに。「1周目: 〇〇と〇〇が食い違っていた → 直した」）
【ユーザーに聞くこと】（自分で決めてはいけないこと。なければ「なし」）
```

---

## 6. NGパターン

- **外部の AI の答えを、そのまま決定として書く**: 壁打ちの答えは言い過ぎや前提の違い（日記の長い文章が前提など）を含む。pukapuka の決まりとデータの形に合わせて書き直し、案として書く
- **変える所だけ読んで書く**: 別のセクションと食い違う（2026-10-05、「拾った順番」の分析を書いたあと、川が順番を決めてしまうことをユーザーに指摘されるまで気づかなかった）
- **専門用語を並べる**: ユーザーが読めない設計書は、決めるのに使えない
